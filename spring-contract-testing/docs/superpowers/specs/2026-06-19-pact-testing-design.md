# Pact Contract Testing — Design Spec

**Date:** 2026-06-19  
**Project:** spring-contract-testing  
**Scope:** Add Pact as a third contract testing approach alongside OpenAPI snapshot testing and Spring Cloud Contract

---

## Context

The project already demonstrates two producer-side contract testing approaches:

1. **OpenAPI snapshot testing** (`OpenApiSnapshotTest`) — diffs the live-generated spec against committed JSON snapshots using openapi-diff.
2. **Spring Cloud Contract** — YAML contract files in the producer drive generated tests; the consumer uses a stub runner against the published stubs JAR.

This spec adds **Pact** as a third approach. Pact is consumer-driven: the consumer owns and defines the contract, generates a pact file, and the producer verifies it independently.

---

## Architecture

### Flow

```
consumer/PactOrderClientTest
  → runs against Pact mock server
  → generates target/pacts/spring-contract-testing-consumer-spring-contract-testing.json

[developer copies pact file]

producer/src/test/resources/pacts/spring-contract-testing-consumer-spring-contract-testing.json
  ← read by PactOrderVerificationTest
  ← verified against the real OrderController via MockMvc
```

The pact JSON file is committed to version control in the producer module, mirroring the pattern used by the existing OpenAPI snapshot JSONs in `producer/src/test/resources/snapshots/`.

No Pact Broker is used. This keeps the demo self-contained.

### Consumer and provider names

- Consumer: `spring-contract-testing-consumer`
- Provider: `spring-contract-testing`

These names must match exactly between consumer and producer.

## Consumer side

**Module:** `consumer/`

### New dependency

```xml
<dependency>
    <groupId>au.com.dius.pact.consumer</groupId>
    <artifactId>junit5</artifactId>
    <version>4.7.0</version>
    <scope>test</scope>
</dependency>
```

> Note: Pact JVM 4.7.x does not yet ship a dedicated `junit6` artifact. The `junit5` artifact is used; Spring Boot 4 / JUnit 6 compatibility is assumed based on JUnit 6 being largely backward-compatible with the JUnit 5 extension API.

### New test: `PactOrderClientTest`

Location: `consumer/src/test/java/codes/dimitri/examples/contracttestingconsumer/PactOrderClientTest.java`

Annotated with `@PactConsumerTest` and `@PactDirectory("target/pacts")`.

Three interactions, each as a `@Pact`-annotated builder method paired with a `@Test` + `@PactTestFor`:

| Interaction | Request | Response |
|---|---|---|
| `findAll` | `GET /orders` | 200, JSON array with one order (type matchers) |
| `findById_found` | `GET /orders/1` | 200, JSON object (type matchers) |
| `findById_notFound` | `GET /orders/999` | 404, empty body |

All body assertions use flexible matchers (`integerType`, `stringType`, `decimalType`) rather than exact values, so the contract survives cosmetic data changes. Each `@Test` method constructs an `OrderClient` pointed at `MockServer.getUrl()` and asserts the client parses the response correctly.

The generated pact file is written to `consumer/target/pacts/`.

## Producer side

**Module:** `producer/`

### New dependency

```xml
<dependency>
    <groupId>au.com.dius.pact.provider</groupId>
    <artifactId>spring7</artifactId>
    <version>4.7.0</version>
    <scope>test</scope>
</dependency>
```

### Committed pact file

The pact JSON generated by the consumer test is copied to:

```
producer/src/test/resources/pacts/spring-contract-testing-consumer-spring-contract-testing.json
```

This is the source of truth the provider verification test reads from.

### New test: `PactOrderVerificationTest`

Location: `producer/src/test/java/codes/dimitri/examples/contracttesting/PactOrderVerificationTest.java`

- `@Provider("spring-contract-testing")` — matches the provider name in the pact file
- `@PactFolder("src/test/resources/pacts")` — reads the committed pact file
- `@WebMvcTest(OrderController.class)` — same setup as `ContractVerifierBase`, no full application context
- `MockMvcTestTarget` — sets the verification target in-process, no running server needed

Provider state setup via `@State`-annotated methods matches the states declared by the consumer:

| State | Mockito stubs |
|---|---|
| `"orders exist"` | `repository.findAll()` returns list with one order |
| `"order 1 exists"` | `repository.findById(1L)` returns the order |
| `"order 999 does not exist"` | `repository.findById(999L)` returns empty |

A single `@TestTemplate` + `@ExtendWith(PactVerificationInvocationContextProvider.class)` method drives verification of all interactions.

---

## Pact file workflow

For this demo, the pact file is managed manually:

1. Run `mvn test` in `consumer/` — pact JSON appears in `consumer/target/pacts/`
2. Copy it to `producer/src/test/resources/pacts/`
3. Commit both the consumer test and the pact file to version control
4. Run `mvn test` in `producer/` to verify

In a real project, step 1-3 would be automated via a Pact Broker.

---

## What is NOT in scope

- Pact Broker integration
- Message/async contract testing
- Pact for the `/orders/paged` endpoint (the consumer `OrderClient` does not call it)
